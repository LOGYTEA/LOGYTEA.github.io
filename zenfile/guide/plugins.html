插件 ​

插件是什么 ​

插件是 ZenFile.exe --plugin <id> 启动的独立进程。

不是独立 exe，不是 DLL，也不 hook 宿主内存：

ZenFile.exe                     ← 宿主：窗口、托盘、文件操作、插件生命周期
└── ZenFile.exe --plugin <id>   ← 插件：独立进程，崩了不影响宿主

为什么要这样设计 ​

需求做法原因
插件崩了不能带崩宿主每个插件一个进程进程间无共享地址空间，panic / 越界 / 死循环都碰不到宿主
不要一堆 exe 要单独升级同一个 exe + --plugin <id>升级一次到位，协议版本永远一致
宿主退了不能留孤儿全部挂进同一个 Job ObjectJOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE，句柄一关内核自动终结全部子进程
插件卡死也要能发现心跳 + 超时（5 秒）进程还活着不代表有用——死循环、弹了个模态框都算卡死
插件别跑在 Job 之外CREATE_SUSPENDED → 入 Job → ResumeThread拉起即入组，杜绝「已跑起来才入组失败」的窗口期

明确不提供：hook 宿主内存、装 API hook、读宿主函数表。 想要新功能就改宿主代码重新编译，而不是塞一段机器码进去。

安装一个插件 ​

在 ZenFile.exe 同级建 plugins/<插件 id>/ 目录，往里放一份 plugin.json：

json
{
  "id": "hello-demo",
  "name": "你好插件",
  "description": "第一个插件",
  "protocol_version": 1,
  "autostart": true,
  "capabilities": ["core.log"]
}

插件不需要编译任何代码——因为插件就是 ZenFile 自己的另一个进程。 重启 ZenFile，打开「设置 - 插件」，面板上就能看到它。

字段必填说明
id✓唯一标识，只能用 [a-z0-9_-]。会进管道名与命令行参数
name✓面板上显示的名字
description一行说明，显示在名字下面
protocol_version填 0 或省略 = 不校验。填了且 ≠ 1 则拒绝拉起
autostarttrue = 宿主启动时自动拉起
capabilities申请的能力。没申请的调用宿主直接拒

plugin.json 必须 UTF-8 无 BOM，且放在插件子目录里，不能写在 plugins/ 根下。

面板状态 ​

「设置 - 插件」里六种状态（PluginState::as_str()）：

状态含义
已禁用你关掉了它
启动中进程已拉起，还没握手
运行中正常
已停止进程没了，正在等重启
无响应心跳超时，会被杀掉重启
启动失败连续崩溃到上限，或清单 / 协议有问题

崩溃隔离 ​

宿主在 100ms 定时器里检查两件事，顺序不能反：

  1. 先判进程还在不在，再判心跳。崩掉的插件 pid 还在句柄表里但已不存活， 先判心跳会把「已崩溃」误记成「无响应」，排查方向都被带偏。
  2. 进程没了 → 崩溃计数 +1 → 连续 4 次后停止重启（MAX_RESTARTS = 3）。

上限是必须的：一个一启动就崩的插件无限重启，会变成「任务管理器里 ZenFile 疯狂拉进程」 的灾难，比崩溃本身更糟。

可申请的能力 ​

字符串含义
clipboard.history读剪贴板历史
screenshot.capture触发截图
taskmgr.snapshot拉取进程 / 性能快照
terminal.open在当前目录开终端
preview.open请求预览文件
core.log写一行日志

能力名点号小写与 PascalCase 两种写法都收（clipboard.history 与 ClipboardHistory 等价）。写错时报错会列出全部可用名字。

当前限制

能力调用链路（call / result）尚未实现。 宿主侧读线程目前只认 hello 和 beat。 当前可验收的范围是：装得上、看得见、进程能拉起、能握手、能持续心跳、崩了能兜住。

排查 ​

宿主把插件现状写进 %TEMP%\zenfile_plugins.log：

前缀时机内容
[discover]扫描目录时每个插件的 id / name / state / pid / crashes / error
[beat]心跳变化时（节流后约 2.5 s 一行）心跳时刻、age、greeted、管道名

判「管道通没通」只能看 [beat] 行的 last_beat 是否在变， 不能靠「没看到失败日志」反推——那不叫验证，那叫没测。

Windows subsystem 下 eprintln! / stderr 拿不到，写文件是唯一可靠手段。

常见问题 ​

面板显示「没有找到插件」plugins/ 目录要和 ZenFile.exe 放在一起，不是 exe 的工作目录。

面板显示「启动失败 · 读不到 plugin.json」 清单路径不对或 JSON 语法错误。必须在插件子目录里，且为 UTF-8 无 BOM。

面板显示「协议版本不兼容」protocol_version 与宿主对不上。宿主当前是 1，填 0 可跳过校验。

面板卡在「启动中」，greeted=false 管道建了但没通。查 [beat] 行的 age_ms 是否持续增长——增长就是没收到心跳。

面板反复「已停止」→「启动失败」 插件进程起来就退。手动跑一次看退出码：3 = 管道连不上，2 = id 非法。

想自己写一个？ ​

看 开始你的第一个插件，那是照着能做完的操作路径。

协议 ​

传输是换行（\n）分隔的 JSON，一行一条消息，经由命名管道 \\.\pipe\ZenFile.{pid}.{safe_id} 传输。

t方向载荷说明
hello插件 → 宿主{"t":"hello","id":...,"protocol":1,"argv":[...]}握手
beat插件 → 宿主{"t":"beat"}心跳，间隔取超时的一半（2500 ms）
shutdown宿主 → 插件—收到后应干净退出，返回 0
call宿主 → 插件{"t":"call","id":N,...}一次能力调用
result插件 → 宿主{"t":"result","id":N,"ok":bool,"payload":...}对 call 的响应

三条纪律：

  1. 心跳必须自己主动发，不能等宿主来问。 宿主判断「插件还活着」的唯一依据就是这条。
  2. 收到 call 必须回响应，哪怕回失败。 不回的话宿主那边挂着一个等不到的请求。
  3. 读消息时半截 JSON 要留着等下一次。 管道是字节流，一次读拿到的很可能只是半条消息。

完整细节见 ZenFile API。
