性能实测 ​

全部数据来自本机实测，没有引用任何厂商宣传口径。每一项都写明了测试方法与口径修正过程， 便于独立复核。凡是拿不到可信数据的地方，直接标注为「未取得」，不做填充、不做估算。

Pulse 的后台开销

它有一个常驻索引服务 Pulse.Index.exe（测量期间占 79～821 MB，随索引进度波动）。 本页 Pulse 的主进程内存不含该服务；但这解释了它为何冷搜最快—— 代价是常驻内存与后台 IO。

方法学 ​

三条硬原则 ​

  1. 三方交错采样（A/B/A 轮换），而不是「测完 A 再测 B 再测 C」。 本机 SSD 性能会随系统负载漂移——同一软件前后两次最大差了 3 倍，不交错会产出假结论。
  2. 取中位数，不取均值，避免单次抖动把结论带偏。
  3. 每轮的目录都是新的：每个被测对象每次都用一个从未被访问过的专属目录， 避开 Shell bag / 文件系统缓存 / 目录元数据 cache 带来的「第二次更快」假象。

口径修正 ①：大文件复制不能看「目标文件长度达标」 ​

ZenFile 与 Explorer 都采用「先预占长度、再填充数据」（set_len / SetEndOfFile）。 于是目标文件在 0.2 秒内就显示成 4.7 GB，此时数据其实还完全没写。

早期按「文件大小达标」判定，得到过 explorer 0.203 秒复制 4GB（= 20143 MB/s） 这种超过 SSD 物理能力的荒谬数字。

改用两级判据：

判据定义是否用于排名
t_size目标文件名义长度达到源长度的耗时❌ 仅作对照展示
t_land用 FILE_FLAG_NO_BUFFERING 绕过系统缓存直读目标尾段、与源比对一致的第一时刻✅ 唯一排名口径

口径修正 ②：必须是跨物理磁盘 ​

早期素材是在 C: 内部同卷同盘生成再复制的，Windows 的缓存与文件系统优化会把真实写盘成本盖掉。 改为 E:（disk 1）→ D:（disk 0），两块不同的物理 SSD。

Explorer 的读数需要解释

explorer.exe 是常驻 shell（还负责桌面与任务栏），它的 RSS 不能全部算作 「这个文件窗口的开销」。实测 Explorer 会为文件窗口另起独立进程：

shell 常驻进程: 140.5 MB（与本次浏览无关，一直存在）
文件窗口进程: 46.9 MB（基线） → 86.3 MB（打开 10 万文件的目录）

所以 Explorer 可比的数字是 46.9 → 86.3 MB。即便按这个更保守的口径， ZenFile 仍是三者中最省的。

一次必须说清楚的过程失误

早期版本这里写的是「3.25 s → 0.040 s，86 倍」。那个数字是错的：

  1. 基准的 engine 臂把扫描逻辑在 benchmark 里重抄了一遍，而生产 collect() 的文件分支当时还走 src.symlink_metadata()——基准测的是一条产品还没走上的路。 现在 engine 臂直接调 pub fn plan_only()，基准和产品不可能再各自漂移。
  2. 即便在重抄的那条路上，也只对上了第一半。第二半的差距来自 resolve_conflict 里每个条目一次 Path::exists()：那是一次完整的文件系统查询， 10 万条目就是 10 万次。拆成三臂后真相才暴露——enumonly(0.033 s) 与 prod(0.94 s) 之间的 0.9 s 全在存在性查询上，与文件系统无关。

修法是 ExistCache：按目录缓存一次 read_dir 快照，每目录只付一次枚举。

UI 响应性 ​

「速度」不只有墙钟时间。一项操作如果在主线程上同步跑， 整个窗口会僵住，用户感知到的慢比计时器上的数字难看得多。

判据用 WM_NULL 的往返延迟（SendMessageTimeoutW，5 秒超时即判卡死），不看操作结果。

删除（20 000 文件 / 20 子目录）：

阶段p50p95worst卡死
空闲基线0.1 ms0.2 ms0.7 ms0
删除中0.0 ms4.8 ms5.5 ms0
删除后0.1 ms0.3 ms0.3 ms0

删除本身耗时 3.3 s，期间主窗口还能切换目录（1.2 s 内列表刷新）—— 即不只是「没卡死」，而是真的在处理用户操作。

批量重命名（3 000 文件）：重命名中 p50 = 0.1 ms、p95 = 0.3 ms、卡死 0。

项目第一名ZenFile 的相对表现
内存占用ZenFile（29.5 MB）领先，约为 Pulse 的 1/7

文件查找Pulse（冷搜）三者同量级，ZenFile 居中间

一句话：ZenFile 的优势在小文件批处理、冷启动加载、内存占用； 曾经唯一的短板（单个大文件的连续写入）已经修掉； 第三个短板（整棵大树复制前的规划扫描）也修掉了，13 倍。

测试中发现并修复的缺陷 ​

缺陷 1：Alt 组合快捷键全部失效。 main.rs 只处理 WM_KEYDOWN， 而带 Alt 的组合键走的是 WM_SYSKEYDOWN——所有 Alt+←/→/↑/↓ 与 Alt+Enter （打开属性页）都没反应。补上 WM_SYSKEYDOWN 后修复。

缺陷 2：transfer.rs 的分块粒度与注释不符。 代码里做了 clamp(块数)， 导致块长被压到 74 MB，与注释描述的 8 MB 不符。第一轮修复它把 CPU/GiB 降了 37%， 第二轮才找到真正的病根——用户态双拷贝路径本身。
